# 면접 대비 기술 포인트 추출

## 목적
LLM-OPT 프로젝트 구현 과정에서 면접에 활용할 수 있는 기술 포인트를 식별하고 정리한다.

## 작동 방식

### 1. 기술적 의사결정 감지
코드를 작성하거나 설계를 논의할 때 다음 패턴을 감지:
- 기술 A 대신 기술 B를 선택한 경우
- 성능/비용/복잡도 Trade-off가 발생한 경우
- 일반적이지 않은 접근 방식을 사용한 경우
- 측정 가능한 개선 결과가 나온 경우

### 2. 출력 형식
감지된 포인트를 다음 형식으로 정리:

```markdown
## [면접 포인트] {주제}

**예상 질문:** "{면접관이 물어볼 법한 질문}"

**답변 구조:**
1. 상황 (어떤 문제가 있었는지)
2. 선택지 (어떤 대안이 있었는지)
3. 결정 (왜 이것을 선택했는지 — 데이터 근거)
4. 결과 (실측 결과 또는 예상 효과)
5. 한계 (솔직히 인정할 부분)

**주의:** 과장 금지. "예상"과 "실측"을 반드시 구분 표기.
```

### 3. 누적 기록
면접 포인트가 생성되면 docs/PHASE_TRACKER.md의 해당 Phase "면접 포인트" 섹션에 추가한다.

## LLM-OPT 주요 면접 주제

다음은 이 프로젝트에서 자주 나올 면접 질문 카테고리:

- **캐싱 전략:** "왜 2-Tier Cache 구조를 선택했나요?"
- **Vector DB 선택:** "Pinecone 대신 Redis를 쓴 이유?"
- **정확도 vs 속도:** "Validation Layer가 오히려 느리게 하지 않나요?"
- **비용 최적화:** "출력 토큰 예측이 틀리면 어떻게 되나요?"
- **Auto-scaling:** "이동 평균 기반 HPA를 선택한 이유?"
- **모니터링:** "어떤 메트릭을 왜 선택했나요?"

## 도원이의 답변 원칙

- 실제 경험 기반으로 답변 (MindGraph-AI에서 겪은 문제 → LLM-OPT 해결)
- 한계를 솔직히 인정 (예: "예측 정확도 ±15%로 완벽하지 않지만...")
- 숫자로 근거 제시 (예: "8ms 추가 비용으로 False Positive를 12%→3.8%로 줄였습니다")
- 이력서에 쓸 수 없는 과장된 표현 사용 금지
