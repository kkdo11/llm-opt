# "파이썬 list와 tuple"을 에스토니아어로 인식한 langdetect — 한국어 기술 문서의 함정

> **환경**: Python 3.12, langdetect 1.0.9, sentence-transformers 3.x
> **측정일**: 2026-02-22

---

## 문제 상황

LLM 프록시에 Semantic Cache를 붙였다. 의미가 유사한 질문은 새로 LLM을 호출하지 않고 캐시에서 반환하는 구조다.

테스트 시나리오:

1. **저장**: "파이썬 리스트와 튜플의 차이점을 설명해줘" → LLM 호출 → 캐시에 저장
2. **조회**: "파이썬 list와 tuple 차이가 뭐야" → Semantic Cache에서 히트해야 함

언어 검증 로직이 있다. 한국어 질문은 한국어 캐시에서만 반환하도록.

```python
# 저장 시
lang = detect("파이썬 리스트와 튜플의 차이점을 설명해줘")  # → 'ko'

# 조회 시
query_lang = detect("파이썬 list와 tuple 차이가 뭐야")    # → ???
```

실행해보니:

```python
from langdetect import detect
detect("파이썬 list와 tuple 차이가 뭐야")
# 'et'
```

**에스토니아어(Estonian)**. 한국어 문장인데.

이 때문에 캐시 검증이 실패한다. 저장된 캐시의 언어는 `'ko'`, 조회 쿼리의 언어는 `'et'` → 언어 불일치 → 캐시 미스 처리.

10개 테스트 쌍 중 이 버그로 인한 캐시 미스가 1건(10%)이었다. 수치만 보면 작아 보이지만, 한국어 개발 질문의 상당수가 영어 기술 용어를 혼용한다는 점에서 실제 운영 환경에서는 훨씬 높은 비율로 발생할 수 있다.

---

## 원인 분석

### langdetect의 동작 방식

langdetect는 문자 n-gram 기반으로 언어를 감지한다. 짧은 텍스트일수록 신뢰도가 낮고, **혼용 텍스트에서는 오인식이 잦다**.

문제가 된 문장을 분해해보자.

```
"파이썬 list와 tuple 차이가 뭐야"
  ↓
한국어: "파이썬", "와", "차이가", "뭐야"
영어:   "list", "tuple"
```

한국어와 영어가 섞여 있다. langdetect는 이 혼용 텍스트에서 n-gram 분포를 계산하는데, `list`, `tuple` 같은 짧은 영어 단어가 에스토니아어 어휘와 우연히 겹쳤다.

실제로 에스토니아어에서 "list"는 흔한 단어다. 에스토니아어는 핀란드어·헝가리어와 같은 핀우그리아어파(Finno-Ugric)로, 영어와 어족이 다르지만 라틴어 기원 외래어를 많이 차용한다. `tuple` 역시 에스토니아어 문서에서 사용되는 단어다. langdetect 입장에서는 한국어 조사("와", "가", "야")가 에스토니아어 어미와 통계적으로 구분이 어렵다.

### 왜 이 문장만 오인식되는가

동일한 질문인데 표현만 다른 두 가지를 비교하면:

```python
detect("파이썬 리스트와 튜플의 차이점을 설명해줘")  # → 'ko' ✅
detect("파이썬 list와 tuple 차이가 뭐야")            # → 'et' ❌
```

차이는 `list`/`tuple` vs `리스트`/`튜플`이다. 영어 기술 용어가 포함된 쪽이 오인식된다.

한국어 기술 문서에서 이런 패턴은 매우 흔하다. "Python list", "React hook", "Docker container"처럼 영어 기술 용어를 한국어 문장 안에 섞어 쓰는 것은 개발자들의 자연스러운 표현 방식이다.

## 시도한 해결책들

### 시도 1: langdetect 파라미터 조정

```python
from langdetect import detect_langs
result = detect_langs("파이썬 list와 tuple 차이가 뭐야")
# [ko:0.4285, et:0.3571, ...]
```

신뢰도가 낮을 때(< 0.7) 'ko'를 기본값으로 설정하는 방법을 고려했다.

**결과: 기각.** 임계값이 임의적이고, 신뢰도 기준이 불안정하다. 영어 텍스트의 신뢰도가 높으면 'en'으로 오판할 수 있다.

### 시도 2: 영어 단어 비율로 언어 판단

문장에서 영어 토큰 비율이 낮으면 한국어로 간주:

```python
import re
def is_korean(text: str) -> bool:
    korean_chars = len(re.findall(r'[가-힣]', text))
    return korean_chars / max(len(text), 1) > 0.3
```

**결과: 기각.** 한국어/영어 비율 기준이 또 다른 임의 파라미터를 만든다. "React로 TODO 앱 만들어줘" 같은 짧은 문장에서 한국어 비율이 낮아 오판 가능.

### 시도 3: 쿼리 정규화 후 langdetect (채택)

근본 원인은 영어 기술 용어가 langdetect를 혼동시키는 것이다. **임베딩 전에 영어 기술 용어를 한국어로 치환**하면 langdetect 입력이 순수 한국어가 된다.

```python
TECH_TERM_MAP = {
    "linked list": "연결 리스트",  # multi-word 먼저 등록
    "dictionary": "딕셔너리",       # "dict"보다 길어서 먼저 매칭됨
    "list": "리스트",
    "tuple": "튜플",
    "dict": "딕셔너리",
    "stack": "스택",
    "queue": "큐",
    # ... (24개 기술 용어)
}

# 긴 용어부터 alternation 패턴 생성 — 단일 패턴으로 한 번에 치환
# re.ASCII: 한국어 문자가 \w로 인식되지 않아 \b 경계가 올바르게 동작
# (없으면 "list와"에서 "와" 앞에 경계가 생기지 않아 치환 누락 발생)
_sorted_terms = sorted(TECH_TERM_MAP.keys(), key=len, reverse=True)
_PATTERN = re.compile(
    r"\b(" + "|".join(re.escape(t) for t in _sorted_terms) + r")\b",
    re.IGNORECASE | re.ASCII,
)

def normalize_query(text: str) -> str:
    """영어 기술 용어를 한국어로 치환한다."""
    return _PATTERN.sub(lambda m: TECH_TERM_MAP[m.group(0).lower()], text)
```

정규화 결과:

```python
normalize_query("파이썬 list와 tuple 차이가 뭐야")
# → "파이썬 리스트와 튜플 차이가 뭐야"

detect("파이썬 리스트와 튜플 차이가 뭐야")
# → 'ko' ✅
```

**중요**: 저장 시와 조회 시 **모두** 동일하게 정규화를 적용해야 한다. 정규화는 임베딩 공간에서의 좌표를 바꾼다. 저장할 때와 조회할 때 좌표가 달라지면 유사도 계산이 틀린다.

---

## 정규화의 부수 효과: 임베딩 유사도도 올랐다

이 수정의 본래 목적은 langdetect 오인식 방지였는데, 뜻밖의 효과가 있었다.

```
정규화 전: sim("파이썬 list와 tuple 차이가 뭐야", "파이썬 리스트와 튜플의 차이점") = 0.87
정규화 후: sim("파이썬 리스트와 튜플 차이가 뭐야", "파이썬 리스트와 튜플의 차이점") = 0.94
```

영어 단어가 한국어로 통일되면 임베딩 모델이 같은 개념을 더 가깝게 인식한다. 오탐 방지와 유사도 향상이 동시에 해결됐다.

---

## 배운 점

**1. langdetect는 혼용 텍스트에서 신뢰할 수 없다**

공식 문서에는 "50자 이상의 텍스트에서 정확도가 높다"고 나온다. 하지만 한국어 + 영어 기술 용어 혼용은 이 가정을 깨뜨린다. 한국어 개발자 커뮤니티에서 이 패턴은 표준적인 표현 방식이다.

**2. 전처리 단계를 일관되게 적용해야 한다**

정규화를 "저장 시에만" 또는 "조회 시에만" 적용하면 임베딩 공간에서 좌표가 어긋난다. 모든 텍스트가 동일한 파이프라인을 거쳐야 유사도 비교가 의미 있다.

**3. 버그 수정과 성능 개선이 동시에 일어났다면, 그게 진짜 근본 원인이다**

langdetect 오인식을 잡으려고 만든 정규화가 임베딩 유사도(0.87 → 0.94)도 올렸다. 처음엔 우연의 일치라고 생각했는데, 이후 생각해보니 이게 "근본 원인에 도달했다"는 신호였다. 임시방편 수정은 하나만 해결되고 다른 하나는 그대로다. 두 가지가 동시에 나아졌다면 공통 원인을 건드린 것이다. 이 경우 "영어 기술 용어의 혼재"가 언어 감지 오류와 임베딩 유사도 저하 모두의 원인이었다.
