## 1. 측정에 대한 태도

**이전**: "캐시 붙이면 빨라지겠지" 하고 구현.

**이후**: 빨라지는 건 맞는데, *얼마나*는 측정 전에 모른다.
실제로 재보니 6,065ms → 0.3ms였다. 예상은 했지만 20,000배라는 수치는 측정 없이는 나올 수 없다.

더 중요한 건: **수치가 있으면 설명이 달라진다.**

> "캐시 붙여서 빨라졌어요" → "캐시 히트 시 평균 6,065ms → 0.3ms, 20,217배 감소했습니다. 이유는 LLM 추론 시간을 완전히 제거했기 때문입니다."

면접에서 전자와 후자를 말하는 사람은 완전히 다르게 보인다.

## 2. 비동기가 왜 필요한지 드디어 체감했다

FastAPI 비동기 관련 이론은 알고 있었다. 근데 이번에 직접 문제를 만났다.

`SentenceTransformer.encode()`는 동기 CPU 연산이다. 이걸 그냥 `await` 없이 호출하면 FastAPI 이벤트 루프가 블로킹된다. 임베딩 계산 중에 다른 요청을 아무것도 못 받는다.

해결: `asyncio.to_thread()`로 스레드 풀에 오프로드.

```python
embedding = await asyncio.to_thread(model.encode, text, normalize_embeddings=True)
```

이 한 줄의 의미를 이제는 설명할 수 있다:
- FastAPI는 단일 이벤트 루프에서 모든 요청을 처리한다
- CPU 연산이 루프를 점유하면 다른 요청이 대기한다
- `to_thread()`는 CPU 작업을 별도 스레드에 넘기고 루프는 다른 요청을 계속 받는다

## 3. 정규식의 유니코드 함정

`re.ASCII` 플래그가 왜 존재하는지 몰랐다.

이번에 한국어 텍스트에서 연도 패턴(`\b(?:19|20)\d{2}\b`)이 매칭되지 않는 버그를 만났다.

원인: Python 3의 `re` 모듈은 기본적으로 유니코드 모드다. `\b`는 `\w`와 `\W` 경계로 정의되는데, 유니코드 모드에서는 한국어 문자 "년"도 `\w`로 인식된다. 그래서 "2024년"에서 "2024" 뒤에 `\b` 경계가 생기지 않는다.

해결: `re.compile(r"\b(?:19|20)\d{2}\b", re.ASCII)` — ASCII 모드에서는 한국어가 `\w`가 아니므로 경계가 정상 작동한다.

**교훈**: 정규식은 언어 환경에 따라 동작이 달라진다. 한국어 텍스트에서 쓸 때는 ASCII/유니코드 모드를 의식적으로 선택해야 한다.

## 4. 임베딩 모델은 "좋은 모델"이 아니라 "맞는 모델"이 있다

HuggingFace에서 가장 많이 쓰이는 `all-MiniLM-L6-v2`를 골랐다. 한국어 paraphrase 유사도를 재보니 0.32~0.77이 나왔다. threshold 0.85에서 히트율 0%.

모델이 나쁜 게 아니라, 영어 학습 데이터로 만들어진 모델을 한국어에 그대로 쓴 게 문제였다.

`paraphrase-multilingual-MiniLM-L12-v2`로 바꿨더니 0.87~0.95.

여기서 배운 것:
1. **"많이 쓰이는"과 "내 문제에 맞는"은 다르다.** 직접 측정해서 확인해야 한다.
2. **모델 교체 비용을 설계에 미리 반영해야 한다.** 두 모델 모두 384차원이라 HNSW 인덱스를 유지할 수 있었다. 만약 768차원 모델을 골랐으면 기존 캐시 전체를 다시 계산해야 했다.

## 5. 버그 수정이 성능 개선을 동시에 가져왔을 때, 그건 근본 원인이다

`langdetect`가 "파이썬 list와 tuple 차이가 뭐야"를 에스토니아어로 인식하는 버그를 발견했다.

해결책으로 쿼리 정규화를 만들었다 — 임베딩 전에 영어 기술 용어를 한국어로 치환.

근데 이 수정이 두 가지를 동시에 해결했다:
1. langdetect 오인식 → 'ko' 정상 인식
2. 임베딩 유사도 0.87 → 0.94 향상

처음엔 부수효과라고 생각했는데, 사실 이게 **근본 원인에 도달했다는 신호**였다. 두 문제의 공통 원인이 "영어 기술 용어의 혼재"였기 때문이다.

임시방편 수정은 하나만 해결된다. 두 가지가 동시에 나아지면 그게 진짜 원인을 건드린 것이다.

## 6. 테스트 격리가 왜 중요한지 직접 겪었다

`TestClient(app)`을 쓰면 FastAPI의 lifespan이 실행된다. lifespan은 Redis에 실제로 연결하고 전역 변수(`_redis_client`, `_quota_tracker` 등)를 초기화한다.

이게 다음 비동기 테스트에서 event loop mismatch로 터진다. `TestClient`가 만든 이벤트 루프와 `pytest-asyncio`의 루프가 다르기 때문이다.

해결: 비동기 테스트 fixture에서 전역 상태를 명시적으로 초기화.

```python
@pytest.fixture
def mock_cache():
    import src.proxy.main as proxy_main
    proxy_main._quota_tracker = None  # 이전 lifespan 잔류 상태 격리
    ...
```

**교훈**: 전역 상태를 가진 코드는 테스트 간 오염이 생긴다. 새 전역 변수를 추가할 때마다 테스트 fixture도 함께 업데이트해야 한다.

## 7. 유사도 threshold 하나로는 의미를 구분할 수 없다

"TCP/UDP 차이"와 "HTTP/HTTPS 차이"는 cosine similarity가 0.78이 나온다. threshold 0.75면 히트된다.

하지만 두 질문의 답은 완전히 다르다. TCP는 전송 계층, HTTP는 응용 계층이다.

Vector Search는 "얼마나 비슷한가"만 알려준다. "어떤 면에서 비슷한가"는 알려주지 않는다. 구조가 비슷한 것(둘 다 "~의 차이점")과 내용이 비슷한 것을 구분하지 못한다.

그래서 Validation Layer가 필요했다. 도메인 지식(TCP와 HTTP는 다른 계층)을 코드로 직접 표현한 것이다.

## 8. 설계 결정에는 근거가 필요하다

이 프로젝트를 하면서 매 결정마다 "왜?"를 기록했다.

- tiktoken 대신 UTF-8 바이트 / 4를 쓴 이유
- ko-sroberta 대신 multilingual을 고른 이유
- 캐시 히트 시 quota를 차감하지 않은 이유

처음엔 귀찮았는데, 나중에 보니 이게 면접 답변 그 자체였다.

"왜 이렇게 했나요?" → PHASE_TRACKER의 의사결정 로그를 그대로 말하면 된다.

근거 없이 결정하면, 나중에 "왜?"라고 물었을 때 "그냥 해봤더니 됐어요"밖에 못 한다.
