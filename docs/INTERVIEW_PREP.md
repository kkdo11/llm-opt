## 2. 핵심 기술 선택 이유

### 2-1. 왜 2-Tier Cache인가?

| 문제 | L1만 있을 때 | L1 + L2 |
|------|-------------|---------|
| "파이썬 정렬 구현해줘" (2회째) | HIT ✅ | HIT ✅ |
| "파이썬 버블소트 코드 짜줘" | MISS ❌ | HIT ✅ (L2) |
| "자바 정렬 구현해줘" | MISS ❌ | MISS ✅ (FP 방지) |

L1은 완전 동일 문자열만 히트한다. 같은 의미의 다른 표현은 L2가 잡는다.
L2에서 잡은 항목은 L1에도 저장(백필)하여 다음 동일 요청은 0.3ms로 처리.

### 2-2. Vector DB — Redis vs Pinecone

**결정: Redis Stack 선택**

| 기준 | Redis Stack | Pinecone |
|------|-------------|---------|
| 비용 | 자체 호스팅 $0 | Starter $70/월 |
| 운영 복잡도 | L1과 동일 인스턴스 | 외부 SaaS 의존 |
| 레이턴시 | ~10~25ms (실측) | ~20~40ms (예상) |
| 기능 | HNSW + JSON 저장 | 벡터만, 별도 KV 필요 |

L1에서 42% 이상 처리되므로 L2의 10~20ms 차이는 전체 평균에 미미하다.
K8s 통합 시 외부 SaaS 의존 없이 동일 클러스터에서 관리 가능.

### 2-3. 임베딩 모델 — all-MiniLM-L6-v2 → paraphrase-multilingual-MiniLM-L12-v2

**결정: 실측 후 교체**

- 초기: `all-MiniLM-L6-v2` (HuggingFace 인기 1위, 영어 최적화)
- 실측: 한국어 paraphrase 유사도 0.32~0.77 → threshold 0.85에서 히트율 0%
- 교체: `paraphrase-multilingual-MiniLM-L12-v2`
- 교체 후: 한국어 paraphrase 유사도 0.87~0.95 ✅
- 교체 비용: 두 모델 모두 384차원 → HNSW 인덱스 재생성 불필요 (설계 시 감안)

### 2-4. Threshold — 왜 0.75인가?

**실측 Threshold 실험 (2026-02-21)**

| Threshold | Hit Ratio (실측) | FP Rate (실측) | 평가 |
|-----------|-----------------|---------------|------|
| 0.75 | 50% → 66.7% | 25% → 0% | **보완 후 채택** |
| 0.80 | 0% | 0% | 히트 불가 |
| 0.85 | 0% | 0% | 히트 불가 |
| 0.90 | 0% | 0% | 히트 불가 |

0.75~0.80 사이에 "절벽"이 있다. 히트 가능한 쌍들의 유사도가 0.75~0.80에 몰려 있어,
0.80 이상으로 올리면 히트율이 0%가 된다.
0.75의 FP 25%는 Validation Layer로 0%로 줄였다.

### 2-5. Validation Layer — 왜 필요한가?

Cosine 유사도만으로는 구분 불가능한 케이스가 있다:

```
"파이썬 정렬" ↔ "자바 정렬"     → 유사도 0.92, 하지만 다른 답변 필요
"TCP/UDP 차이" ↔ "HTTP/HTTPS 차이" → 유사도 0.78, 다른 계층의 프로토콜
"2024년 GDP" ↔ "2023년 GDP"     → 유사도 0.95, 다른 사실
```

3단계 순차 검증 (단락 평가, 빠른 종료):
1. **언어 일치**: 한→영 혼용 오인식 방지
2. **숫자/연도/버전**: 시간 의존 정보 보호
3. **기술 키워드**: 프로그래밍 언어, 네트워크 프로토콜 불일치 차단

순서 근거: 언어 불일치가 가장 빠른 조기 종료. 숫자 불일치는 사실 왜곡 위험이 크므로 우선 처리.

### 2-6. 토큰 예측 — 왜 tiktoken 대신 UTF-8 바이트/4인가?

- Qwen 2.5 14B는 자체 tokenizer 사용 → tiktoken과 토큰 경계 다름
- UTF-8 바이트 / 4: ±30% 오차지만, 임계값이 150%이므로 허용 범위 충분
- tiktoken 의존성 추가 = 유지보수 부담, 정확도 향상 미미
- 단순한 구현이 측정 가능하고 디버깅하기 쉬움

### 2-7. KNN k=3 — 왜 k=1이 아닌가?

실험 중 k=1에서 발견한 문제:
```
"파이썬 버블소트 코드 짜줘" → KNN 1위: "오버피팅이 무엇인지 설명해줘" (sim=0.948)
"파이썬 버블소트 코드 짜줘" → KNN 2위: "파이썬으로 버블 정렬 구현해줘" (sim=0.890)
```

paraphrase 모델이 문장 구조(`~해줘`, `~설명해줘`)를 과도하게 반영하여 토픽이 다른 원본을 1위로 반환.
k=3으로 확장 후 Validation Layer를 순차 적용해 정확한 원본을 선택.

## 3. 예상 면접 질문 + 모범 답변

### [카테고리 1] 프로젝트 동기 / 배경

---

**Q. 이 프로젝트를 왜 만들었나요?**

**A.**
MindGraph-AI(개인 지식 그래프 시스템)를 운영하면서 Qwen 2.5 14B 모델을 RTX 4080 Super(16GB VRAM)에 올려 쓰고 있었습니다. 운영 중에 두 가지 비효율을 발견했습니다.

첫 번째, 동일한 질문이 반복해서 들어올 때마다 GPU가 6초씩 추론을 반복했습니다.
두 번째, "파이썬 정렬 구현해줘"와 "파이썬 버블소트 코드 짜줘"처럼 같은 의미의 표현도 매번 새로 추론했습니다.

이걸 해결하기 위해 LLM 호출 경로 앞에 프록시 레이어를 만들었습니다. Semantic Caching으로 동일/유사 질문을 걸러내고, 트래픽 제어로 비용 폭탄을 차단하는 구조입니다.

**한계:** 실 MindGraph 연동은 현재 진행 중입니다(Phase A). 실측치는 독립 실험 환경에서 측정했습니다.

---

**Q. 혼자서 처음부터 설계했나요? 어떻게 접근했나요?**

**A.**
Phase별로 나눠서 접근했습니다. 먼저 단순한 것(Hash Cache)을 구현하고 측정한 다음, 측정 결과를 보고 다음 단계(Semantic Cache, 비용 보호)를 결정했습니다.

처음부터 Semantic Cache를 설계하지 않은 이유는, Hash Cache만으로도 중복 50% 시나리오에서 API 호출을 50% 줄였기 때문입니다. 이 수치를 보고 나서 "그러면 유사 질문은 얼마나 커버할 수 있을까?"라는 질문이 자연스럽게 나왔고, Phase 2로 이어졌습니다.

### [카테고리 2] 캐싱 아키텍처

---

**Q. 왜 2-Tier Cache 구조를 선택했나요?**

**A.**
L1(Hash Cache)과 L2(Semantic Cache)는 해결하는 문제가 다릅니다.

- L1: 완전히 같은 질문 → MD5 해시 조회, O(1), 0.3ms. 비용 없음.
- L2: 의미상 같은 다른 표현 → 임베딩 + 벡터 유사도 검색, ~25ms.

L1만으로는 표현이 조금만 달라도 LLM을 호출합니다. L2만으로는 임베딩 계산 비용이 항상 발생합니다.

둘을 계층으로 쌓으면, 동일 표현은 L1이 0.3ms로 처리하고 유사 표현만 L2로 내려갑니다. L2에서 히트한 항목을 L1에도 저장(백필)하면 다음번엔 L1이 처리합니다.

**실측:** 중복 50% 시나리오에서 L1 히트 50%, L2 히트 66.7%. 캐시를 통과해야 LLM을 호출합니다.

---

**Q. 캐시 키를 MD5로 만든 이유는 무엇인가요?**

**A.**
```python
def cache_key(messages: list[dict]) -> str:
    serialized = json.dumps(messages, ensure_ascii=False, sort_keys=True)
    return f"llm:cache:{hashlib.md5(serialized.encode()).hexdigest()}"
```

세 가지 이유입니다.
1. `sort_keys=True`로 JSON 키 순서를 고정하여 같은 메시지가 항상 같은 해시를 만듭니다.
2. MD5 해시로 키 길이를 32자로 고정합니다. 원본 메시지가 수천 자여도 Redis 키가 짧고 일정합니다.
3. 캐시 충돌 방지가 목적이므로 SHA-256의 암호학적 안전성은 불필요합니다. MD5가 더 빠릅니다.

---

**Q. L2 캐시 히트 시 L1에도 저장하는 이유는?**

**A.**
의미상 같은 질문을 한 번 했다면 다시 같은 표현으로 물어볼 확률이 높습니다. L2에서 히트했다는 건 "이 내용의 캐시가 있다"는 뜻이므로, 이후 동일 표현 요청은 임베딩 계산 없이 L1이 0.3ms로 처리하게 됩니다.

추가 비용: Redis `SET` 하나. 얻는 이득: 이후 동일 요청 25ms → 0.3ms.

---

### [카테고리 3] Semantic Cache / 임베딩

---

**Q. 임베딩 모델을 왜 paraphrase-multilingual-MiniLM-L12-v2로 선택했나요?**

**A.**
처음엔 HuggingFace에서 가장 많이 쓰이는 `all-MiniLM-L6-v2`를 썼습니다. 그런데 한국어 paraphrase 쌍의 유사도를 실측해보니 0.32~0.77이 나왔고, threshold 0.85에서 히트율이 0%였습니다.

원인을 분석하니 이 모델은 영어 데이터로 학습됐기 때문에 한국어 문장의 의미적 유사도를 제대로 측정하지 못했습니다.

`paraphrase-multilingual-MiniLM-L12-v2`로 교체하니 같은 쌍의 유사도가 0.87~0.95로 올랐습니다.

교체 시 중요했던 점: 두 모델이 모두 384차원이어서 Redis HNSW 인덱스를 다시 만들지 않아도 됐습니다. 만약 768차원 모델을 썼다면 기존 캐시를 전부 무효화해야 했을 것입니다. 처음부터 차원을 유지할 수 있는 후보군 안에서 선택했습니다.

---

**Q. COSINE 유사도를 어떻게 계산하나요?**

**A.**
Redis Stack HNSW 인덱스는 COSINE **거리**를 반환합니다 (0=동일, 2=완전 반대). 유사도로 변환하는 공식은 `similarity = 1.0 - distance`입니다.

한 가지 함정이 있었는데, KNN 쿼리에서 `AS score`로 별칭을 지정하면 redis-py `Document` 객체의 기본 `score` 속성(항상 0)이 우선됩니다. `AS vec_score`로 다른 이름을 쓰고 `getattr(doc, "vec_score")`로 접근해야 합니다.

---

**Q. SentenceTransformer.encode()를 asyncio.to_thread()로 감싼 이유는?**

**A.**
`encode()`는 동기 CPU 연산입니다. FastAPI는 단일 이벤트 루프에서 모든 요청을 처리하는데, 동기 CPU 연산이 루프를 점유하면 그 시간 동안 다른 요청을 받을 수 없습니다.

`asyncio.to_thread()`는 CPU 작업을 별도 스레드 풀에 오프로드하고, 이벤트 루프는 계속 다른 요청을 받습니다. 임베딩 계산 중에도 다른 요청이 L1 캐시에서 응답받을 수 있습니다.

---

**Q. 쿼리 정규화(normalizer.py)는 왜 필요했나요?**

**A.**
두 가지 문제를 한 번에 해결했습니다.

첫 번째, 임베딩 유사도 문제입니다. "파이썬 list와 tuple 차이가 뭐야"와 "파이썬 리스트와 튜플 차이가 뭐야"는 같은 의미인데, 영어 기술 용어(`list`, `tuple`)가 섞이면 임베딩이 한국어 버전과 달라져 유사도가 낮게 나왔습니다. TECH_TERM_MAP으로 영어를 한국어로 치환하면 저장 시와 검색 시 임베딩 공간이 일치합니다.

두 번째, langdetect 오인식 문제입니다. "파이썬 list와 tuple 차이가 뭐야"를 langdetect에 그대로 넣으면 에스토니아어(`et`)로 인식했습니다. 정규화 후 "파이썬 리스트와 튜플 차이가 뭐야"로 바꾸면 `ko`로 정상 인식됩니다. 두 번 수정하지 않고 하나의 수정으로 두 문제를 해결했습니다.

---

### [카테고리 4] Validation Layer

---

**Q. Validation Layer가 오히려 레이턴시를 늘리지 않나요?**

**A.**
예상 오버헤드는 +5~10ms입니다. 대신 얻는 것은 False Positive 제거입니다.

False Positive가 발생하면 "자바 정렬" 질문에 "파이썬 정렬" 답변을 주게 됩니다. 이건 5ms 절약보다 훨씬 큰 피해입니다. LLM 프록시에서 잘못된 응답을 반환하면 사용자 신뢰를 잃습니다.

트레이드오프 관점에서: 5ms 레이턴시 비용으로 잘못된 응답을 막는다면, L2 히트의 전체 레이턴시 25ms 중 5ms는 허용 범위입니다. LLM 직접 호출(6,065ms)보다는 여전히 240배 빠릅니다.

---

**Q. Validation Layer의 3단계 순서는 어떻게 정했나요?**

**A.**
단락 평가(short-circuit evaluation)를 최대화하는 순서입니다.

1. **언어 일치** — 가장 빠른 조기 종료. 문자열 비교 하나로 끝납니다. 한국어 쿼리가 영어 캐시를 히트하는 경우를 막습니다.
2. **숫자/연도/버전** — 정보 왜곡 위험이 가장 큰 케이스입니다. "2024년 GDP"와 "2023년 GDP"는 유사도 0.95지만 전혀 다른 사실을 담고 있습니다.
3. **기술 키워드** — 프로그래밍 언어, 네트워크 프로토콜. 이 케이스가 1, 2보다 드물어 마지막에 배치했습니다.

불확실할 때는 항상 Miss로 처리합니다. 느리지만 정확한 응답이 빠르지만 틀린 응답보다 낫습니다.

---

### [카테고리 5] 비용 보호

---

**Q. 출력 토큰 예측이 틀리면 어떻게 되나요?**

**A.**
예측 오차는 ±30% 수준입니다. (실측 전 예상치, 실 Ollama 스트리밍 측정 미완)

중단 임계값을 예측 상한의 150%로 설정했습니다. 즉 예측이 ±30% 틀려도 임계값이 150%이므로 정상 응답을 끊지 않습니다. 의도적으로 허용 범위를 넉넉하게 잡았습니다.

비용 폭탄의 정의는 "예측 상한의 150%를 초과하는 응답"입니다. 이 경우 `[TRUNCATED]`를 붙이고 스트림을 중단합니다.

```python
token_limit = int(predicted_max * 1.5)
if current_tokens > token_limit:
    accumulated_text += "[TRUNCATED]"
    break
```

**한계:** 실 Ollama 스트리밍으로 실측한 차단율 데이터는 아직 없습니다. 예상치는 >95%입니다.

---

**Q. 캐시 히트 시 왜 할당량을 차감하지 않나요?**

**A.**
할당량의 목적은 GPU/API 실비용을 제어하는 것입니다. 캐시 히트는 LLM 추론이 없으므로 GPU를 쓰지 않습니다.

할당량을 "실제로 소비한 컴퓨팅 비용"의 기준으로 정의했기 때문에, 캐시에서 온 응답은 차감 대상이 아닙니다. 부수 효과로, 캐시 히트율이 높은 사용자는 동일한 할당량 안에서 더 많은 유효 요청을 처리할 수 있습니다.

---

**Q. 월간 할당량 초기화를 어떻게 자동화했나요?**

**A.**
Redis `EXPIREAT`으로 월말 자동 만료를 설정했습니다. cron 없이 Redis 자체 TTL 기능만 씁니다.

```python
# Redis 키: llm:quota:{user_id}:{YYYYMM}
# 월말 마지막 날 23:59:59에 자동 만료
import calendar
last_day = calendar.monthrange(year, month)[1]
expiry = datetime(year, month, last_day, 23, 59, 59).timestamp()
await redis.expireat(key, int(expiry))
```

다음 달 첫 요청 때 키가 없으면 `INCRBY`가 0에서 시작해 새 키를 만듭니다. 초기화 로직이 별도로 필요 없습니다.

---

### [카테고리 6] 테스트 / 코드 품질

---

**Q. 107개 테스트를 어떻게 구성했나요?**

**A.**
외부 의존성(Redis, LLM)을 모두 mock으로 처리하여 단위 테스트를 독립적으로 만들었습니다.

- `test_cache.py`: L1 Hash Cache (key 생성, TTL, GET/SET)
- `test_vector_cache.py`: L2 HNSW (저장, 검색, threshold, bytes/str 변환)
- `test_validator.py`: Validation Layer 25개 (언어/숫자/기술 키워드, 엣지 케이스)
- `test_normalizer.py`: 쿼리 정규화 10개 (한→영, 영→한, 혼용)
- `test_token_predictor.py`: 토큰 예측 20개 (유형별 패턴)
- `test_quota_tracker.py`: 할당량 추적 14개 (INCRBY, 80% 경고, 월말 만료)
- `test_proxy.py`: 통합 흐름 20개 (L1 히트, L2 히트, LLM 호출, 429 응답)

`SEMANTIC_CACHE_ENABLED=false` 환경변수로 SentenceTransformer 로딩을 막아 테스트 실행 시간을 ~5초로 유지했습니다.

---

**Q. FastAPI TestClient와 lifespan 테스트 시 어떤 어려움이 있었나요?**

**A.**
`with TestClient(app) as client:` 블록에 진입하는 순간 lifespan이 실행되어 `_redis_client` 같은 전역 변수가 실제 값으로 초기화됩니다. 블록 진입 전에 주입한 mock이 lifespan에 의해 덮어씌워지는 문제가 있었습니다.

해결책은 `with` 블록 **내부**에서 mock을 재주입하는 것입니다.

```python
with TestClient(app) as client:
    # lifespan 완료 후 mock 재주입
    proxy_main._redis_client = mock_redis
    response = client.get("/health")
```

추가로 Phase 3에서 `_quota_tracker`를 전역 변수로 추가한 후, 이전 테스트의 lifespan에서 만든 Redis 클라이언트가 다음 테스트의 event loop에서 참조되는 문제가 생겼습니다. fixture에서 명시적으로 `None`으로 초기화해 해결했습니다.

---

### [카테고리 7] 아키텍처 / 설계

---

**Q. Pinecone이나 Weaviate 같은 전용 Vector DB를 쓰지 않은 이유는?**

**A.**
세 가지 이유입니다.

첫 번째, L1 Hash Cache와 같은 Redis 인스턴스를 씁니다. 별도 인프라 없이 Redis Stack 하나로 두 캐시 레이어를 관리할 수 있습니다.

두 번째, K8s 배포 시 외부 SaaS 의존을 줄이고 싶었습니다. Pinecone은 $70/월이고, 장애 시 L2 캐시 전체가 영향받습니다.

세 번째, L1에서 이미 42~50%를 처리하므로 L2에 Pinecone 수준의 고성능이 필요하지 않습니다. Redis HNSW의 ~25ms 레이턴시로 충분합니다.

**한계:** 캐시 항목이 수백만 건으로 늘어나면 Redis 메모리 비용이 올라갑니다. 그 규모에선 전용 Vector DB 재검토가 필요합니다.

---

**Q. 비동기로 구현한 이유는?**

**A.**
FastAPI는 비동기 프레임워크이고, 이 서비스의 대부분의 시간은 I/O 대기(Redis 조회, LLM API 호출)입니다. 동기로 구현하면 한 요청의 LLM 응답을 기다리는 동안 다른 요청을 전혀 처리하지 못합니다.

CPU 바운드 작업(SentenceTransformer.encode, langdetect)은 `asyncio.to_thread()`로 스레드 풀에 오프로드했습니다. 이벤트 루프를 점유하지 않으면서 CPU 작업을 병렬 처리합니다.

---

**Q. 이 프로젝트에서 가장 어려웠던 부분은?**

**A.**
Threshold 실험에서 예상과 다른 결과가 나왔을 때 원인을 분석하는 과정이었습니다.

목표는 `FP < 5%`, `Hit > 40%` 동시 달성이었는데, 실험 결과 모든 threshold에서 둘 중 하나가 달성되지 않았습니다. 0.75에서는 FP 25%, 0.80 이상에서는 Hit 0%.

원인을 찾아보니 세 가지가 있었습니다.
1. k=1 KNN이 문장 구조가 유사한 엉뚱한 원본을 선택
2. 유사도 분포가 0.75~0.80 사이에 몰려 있어 threshold 이동이 의미 없음
3. `langdetect` 오인식 버그 (한국어를 에스토니아어로 인식)

각 원인을 코드로 수정하고 재실험했더니 Hit 66.7%, FP 0%를 달성했습니다. 실패를 원인 분석 없이 그냥 넘기지 않고, 각 원인을 독립적으로 수정하고 검증한 과정이 인상적인 경험이었습니다.

---

### [카테고리 8] 한계 및 개선 방향

---

**Q. 이 시스템의 한계는 무엇인가요?**

**A.**
솔직하게 말하면 세 가지입니다.

첫 번째, **실 MindGraph 연동이 아직 없습니다.** 실측치는 독립 실험 환경에서 측정했습니다. 실제 운영 트래픽 패턴에서의 히트율은 아직 모릅니다.

두 번째, **임베딩 모델 한계.** "오버피팅이란 무엇인가요?"와 "오버피팅이 무엇인지 설명해줘"는 같은 의미인데 유사도가 0.57로 threshold 미달입니다. 현재 모델이 문장 구조에 과민반응하는 경향이 있습니다.

세 번째, **스트리밍 비용 측정.** Phase 3에서 SSE 스트리밍 차단 로직을 구현했지만, 실 Ollama 스트리밍으로 측정한 차단율 데이터가 없습니다. 예상치(>95%)와 실측치의 차이가 얼마나 될지 아직 모릅니다.

---

**Q. 개선한다면 무엇부터 하겠습니까?**

**A.**
우선순위 순서로 말씀드리면:

1. **실 MindGraph 연동 (Phase A):** Ollama 호환 엔드포인트(`/api/chat`)를 추가하면 실제 트래픽으로 모든 미측정 항목을 채울 수 있습니다.

2. **한국어 특화 임베딩 모델 검토 (B방안):** `ko-sroberta-multitask`나 `KoSimCSE-roberta`로 교체하면 토픽 다른 원본 간 유사도를 낮추고(흡수 현상 감소), 동의어 paraphrase 유사도를 높일 수 있습니다. 다만 768차원이면 HNSW 인덱스 재생성이 필요하여 설계상 비용이 있습니다.

3. **K8s + Custom HPA (Phase 4):** 이동 평균 기반 Scale Up/Down으로 트래픽 급증에 대응합니다.
